## 1. 一句话定位

**给"需要定期从一个或多个网站收集结构化信息"的人用的本地采集工作台**：配好地址、点开始、拿到一张能检索、能看趋势、能导出的表。

不是通用爬虫 SaaS，不追求百万级并发，追求**合规、可解释、数据直接能用**。

## 2. 目标用户与场景

| 用户 | 场景 | 现在怎么做 | 我们的价值 |
|---|---|---|---|
| 写文献综述的学生 | 从学院/期刊站点收集论文题录 | 手工复制粘贴到 Excel | 一次配置，增量采集，字段直接成表 |
| 需要跟公告的人 | 每周看某站点有没有新通知 | 每天手动刷新 10 个页面 | 定时增量，新内容高亮提醒 |
| 小团队做竞品监测 | 收集对手官网的产品/价格更新 | 人工整理 | 变更检测 + 导出对比报告 |

三类用户有一个共同点：**站点固定、量不大、要的是结构与变化，不是海量抓取**。

## 3. 与市面工具的差异

| 工具 | 强项 | 短板 | 我们的位置 |
|---|---|---|---|
| 八爪鱼 / 后羿采集器 | 可视化点选、模板多 | 重、要登录、高级功能收费、黑盒 | 轻量、代码可控、讲义级可解释 |
| Bright Data / 代理网络 | 规模、反反爬 | 贵、面向企业 | 不做代理，做本地小规模 |
| Scrapy 生态 | 工程化、可扩展 | 纯框架，没有界面与数据层 | 我们自带 UI 与数据治理 |
| 浏览器插件类 | 即装即用 | 只能单页、无任务概念 | 我们有多页任务与历史 |

**差异化三条**（也是答辩时最能讲的三条）：

1. **可解释**：每个被跳过的 URL 都有原因（深度/同域/后缀/robots/去重），日志里查得到；
2. **合规优先**：robots 默认开、按域限速、UA 可识别，不做反反爬；
3. **数据可用**：不是"抓完一堆 HTML"，而是直接得到可检索、可对比、可导出的结构化数据。

## 4. 三层能力模型

```
        ┌─────────────── 价值层（数据能干什么）───────────────┐
        │ 检索 · 看板 · 增量监测 · 报告导出 · 标签/收藏 · API │
        └───────────────────────▲───────────────────────────┘
        ┌─────────────── 治理层（跑得稳、管得住）─────────────┐
        │ 任务历史 · 断点续爬 · 失败队列 · 站点配额 · 内容去重│
        └───────────────────────▲───────────────────────────┘
        ┌─────────────── 采集层（已经做完）──────────────────┐
        │ 队列三策略 · robots · 限速 · 六字段抽取 · SQLite    │
        └───────────────────────────────────────────────────┘
```

v1 只完成了最底层。**"没用"的根源是价值层是空的**——数据进来了，但只能拿来看一眼。

## 5. 功能清单与优先级

### P0（决定"像个产品"）

| 功能 | 说明 | 对应痛点 |
|---|---|---|
| 结果检索 | 标题/摘要/URL 关键词搜索 + 站点筛选 + 时间排序 | 100 条以上就找不着 |
| 数据看板 | 站点分布、抓取时间分布、字段完整率、成功率 | 报告没图、看不出效果 |
| 任务历史 | 每次运行一条记录（参数、耗时、条数），可对比 | 关掉就忘，无法复现 |
| 增量采集 | 记住已抓 URL，第二次只抓新的 | 每次全量重抓 |
| 一键导出 | CSV / JSON / Markdown 报告 | 数据出不去 |

### P1（决定"好用"）

| 功能 | 说明 |
|---|---|
| 断点续爬 | 队列落库，中断可继续 |
| PDF 下载 | 带大小上限，落到 `data/pdf/` |
| 定时任务 | 每天/每周自动跑一次（APScheduler 或系统计划任务） |
| 标签与收藏 | 给条目打标签、标星，支持按标签导出 |
| 内容去重 | 正文 simhash，避免同文不同 URL 重复 |
| 失败重试队列 | 失败条目单独重试，不用整轮重跑 |

### P2（决定"加分"）

| 功能 | 说明 |
|---|---|
| 变更提醒 | 目标页内容变化时标红，生成 diff |
| 词频/热词 | 中文分词后出 TopN 关键词（需引入 jieba） |
| 简易 API | `/api/pages` 供其他程序取数 |
| 多任务并行 | 同时跑多个采集任务 |
| 图表导出 | 看板图导出 PNG，直接进报告 |

## 6. 页面结构（Web）

```
/            工作台     参数 → 开始 → 实时日志 → 结果表（已实现）
/data        数据       检索、筛选、排序、分页、详情抽屉、批量导出
/dashboard   看板       站点分布、时间分布、完整率、成功率、速率曲线
/tasks       任务       历史运行列表、参数对比、重跑
/settings    设置       默认参数、UA、合规开关、数据库位置
```

每页只做一件事，避免工作台变成"什么都有但都难用"。

## 7. 数据模型扩展

```sql
-- 每次运行一条，支撑任务历史与对比
CREATE TABLE runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    started_at TEXT, finished_at TEXT,
    strategy TEXT, seeds TEXT,
    max_depth INTEGER, max_pages INTEGER,
    fetched INTEGER, failed INTEGER, dup INTEGER,
    elapsed_ms INTEGER, note TEXT
);

-- pages 增列
ALTER TABLE pages ADD COLUMN content_hash TEXT;   -- 正文 simhash，做内容去重
ALTER TABLE pages ADD COLUMN run_id INTEGER;      -- 归属哪次运行

-- 全文检索（SQLite 自带 FTS5，不引入新依赖）
CREATE VIRTUAL TABLE pages_fts USING fts5(
    title, abstract, keywords, url UNINDEXED, content='pages', content_rowid='id'
);
```

`runs` + `run_id` 是"任务历史"和"增量采集"的地基，建议放在批 1 先做。

## 8. 技术选型

| 选择 | 理由 | 被否方案 |
|---|---|---|
| Flask | 单文件可跑、概念少（路由 + 请求 + 响应），调试直观 | FastAPI（async/pydantic 概念多，新手成本高）；Django（过重） |
| 原生 HTML/CSS/JS | 页面只有 5 个，不需要构建链；改一行刷新就见效 | React/Vue（要 node、构建、依赖，演示多一层风险） |
| SSE 推日志 | 单向推送够用，浏览器自带重连 | WebSocket（双向，过度设计） |
| SQLite（含 FTS5） | 零部署、单文件、自带全文检索 | MySQL/Elasticsearch（本机演示没必要） |
| SVG 手绘图表 | 不依赖 CDN，断网也能出图 | ECharts CDN（断网就白屏） |

**新增依赖只有 flask**，其余仍是标准库。这条要写进报告的"工具选型"一节。

## 9. 关键交互原则

1. **永远有反馈**：点开始后 100ms 内界面必须变（状态、按钮禁用），抓取失败要有可见日志。
2. **空状态有引导**：没数据时表格显示"还没有结果，先点开始采集"，而不是空白。
3. **错误可执行**：提示"发生了什么 + 怎么办"，不直接抛 Python 异常文本。
4. **危险操作二次确认**：清空数据库、覆盖导出文件。
5. **断网可用**：所有静态资源本地化，不依赖 CDN。

## 10. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M1（已完成）** | Web 骨架：参数、启停、SSE 日志、结果表、导出、清空 | 浏览器里跑通一次完整采集 |
| **M2** | 数据页：检索（FTS5）、筛选、排序、详情、批量导出 | 200 条数据下检索 < 100ms |
| **M3** | 看板 + 任务历史（runs 表） | 出 4 张图；历史列表可对比两次运行 |
| **M4** | 增量采集 + 定时任务 + 变更提醒 | 第二次运行只抓新增；变更标红 |
| **M5** | 打磨：空状态、快捷键、打包成单文件、演示站点 | 断网演示 5 分钟不掉链子 |

## 11. 风险与取舍

| 风险 | 影响 | 对策 |
|---|---|---|
| 功能铺太开 | 每个都半成品 | 严格按 P0 → P1 顺序，一个功能做完再做下一个 |
| Web 层变厚 | 演示多一个故障点 | 保留命令行入口 `python -m crawler.cli`，UI 挂了也能证明引擎可用 |
| FTS5 中文分词差 | 检索不准 | 用 `unicode61` 分词 + LIKE 兜底；中文分词列为 P2 |
| 报告写不完 | 40% 分数 | 每个里程碑产出一张图/一张表，边做边写 |

## 13. 白话版：前面那些词是什么意思

| 词 | 白话解释 |
|---|---|
| **M1–M5** | 里程碑，就是"分五步走"的刻度。M1 能跑通 → M2 数据能查 → M3 能看趋势 → M4 能自动更新 → M5 打磨。不是五个新功能名 |
| **看板** | 一页图表（dashboard）：哪个站抓得多、每天抓多少、字段缺多少、成功率高不高。报告里能直接截图用 |
| **定位** | 这个产品"给谁用、解决什么问题"。定位不同，功能优先级完全不一样 |
| **价值层** | 数据抓回来之后能干什么（检索、看板、报告、提醒） |
| **主入口** | 我造的词，指"演示时默认用哪个"。三个入口共用同一个引擎，代码上没有主次 |

## 14. 定位三选一（这是最需要你拍板的）

先给背景：市面上的爬虫产品分三类——

1. **可视化采集器**（八爪鱼、后羿、Octoparse）：卖"谁都能抓"，强在模板与点选；
2. **数据/代理服务**（Bright Data、Apify、ScraperAPI）：卖"大规模、不被封"，面向企业；
3. **垂直数据产品**（电商比价、舆情监测、招聘聚合）：卖"抓来干嘛"，用户不关心爬虫。

**课程作业做成第 1 类必输**（打不过成熟产品）；做成第 3 类反而容易出彩，因为考察点变成"你懂不懂这个场景"。

| | A. 站点更新监测助手 | B. 垂直资讯日报 | C. 通用采集工作台（当前） |
|---|---|---|---|
| 用户 | 学生/行政/小团队，固定盯 3~10 个站 | 技术从业者，追 GitHub/arXiv/ HN | 不特定 |
| 核心痛点 | "又错过通知了"，每天手动刷 | 信息过载，没时间筛 | 说不清楚 |
| 市面替代 | RSS（基本死了）、公众号、八爪鱼（太重） | 各类 newsletter、聚合站 | 八爪鱼、Octoparse |
| 差异化 | 订阅式、只报新增、可检索、可归档 | 自己选源、自动生成早报 | 弱 |
| 工作量 | 中（监测 + 变更检测） | 中（多源适配 + 排版） | 大 |
| 演示效果 | 直观："昨天有没有新通知" | 有趣："一键生成今日简报" | 平庸："你看我能抓网页" |
| 风险 | 要找到 2~3 个能公开抓的站 | 依赖外网、易被限流 | 什么都不精 |

**我的建议：选 A，把 B 当彩蛋。**
理由：A 的痛点真实（"错过通知"人人有共鸣）、合规最容易讲（校园/政府站公开、robots 友好）、演示有对照（昨天的数据 vs 今天的新增），而且它天然把你已有的能力串起来：定时采集 + 去重（判断新旧）+ 变更检测 + 检索 + 导出。
等 A 跑顺了，加一个"生成今日简报"的导出（Markdown/PDF），就是 B 的彩蛋。

如果你更想要"有意思"，选 B 也行，但要在报告里说清楚合规边界（只用公开 API / robots 允许的页面）。
